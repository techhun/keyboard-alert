# Restock Android

키보드 관련 상품의 옵션별 재고를 주기적으로 확인하고 재입고 시 Android 알림을 보내는 개인용 모니터링 앱입니다.

## 현재 기능

- 여러 상품 등록 및 상품별 알림 ON/OFF
- 상품별 여러 옵션 선택 및 옵션 수정/삭제
- 옵션명 검색, 그룹 접기/펼치기, 선택 옵션 필터
- 재고 없음 → 재고 있음 전환 시 재입고 알림
- SmartStore 선택 옵션의 잔여 수량이 기준 이하로 내려가면 재고 부족 알림 (기본 5개, 설정에서 1~999개 변경 가능)
- 선택 옵션 재고가 0개면 카드 상태를 `재고 없음 0/N`으로 표시
- SmartStore와 SWAGKEY 상품 동시 감시
- Foreground Service 기반 주기 감시
- 10초 / 15초 / 30초 / 60초 조회 주기 (기존 설정은 변경하지 않음)
- 여러 상품 감시 시 요청 간 최소 5초 간격 보장
- 여러 상품 순회 중 현재 상품과 WebView 페이지/응답의 상품번호를 검증해 지연 응답이 다른 상품 상태를 덮어쓰지 않도록 보호
- 일시적인 페이지 상태/파싱/5xx 오류는 제한적으로 재시도
- 백그라운드 SmartStore 조회는 PAGE_CAPTURE/PAGE_STATE를 두 번 먼저 확인한 뒤에만 내부 상품 API fallback을 1회 사용
- HTTP 204가 발생하면 상품 페이지를 1회 재로드하고 PAGE_CAPTURE/PAGE_STATE만 다시 확인하며, 복구 회차에서는 내부 API를 재호출하지 않음
- HTTP 429는 기존 전역 요청제한 backoff 정책 유지
- 네트워크 끊김 자동 대기 및 복구
- HTTP 429 요청 제한 응답 시 지수 백오프
- 단일 HTTP 204는 해당 상품 실패로만 처리하며, 2분 안에 최종 204가 3회 반복되거나 서로 다른 SmartStore 상품 3개 이상에서 이어지면 전체 SmartStore 조회를 5분 보호 대기해 연속 호출을 멈춤
- 수동 옵션 조회 중 백그라운드 SmartStore 감시를 잠시 멈춰 동시 요청 방지
- 조회 콜백을 단일 체인으로 직렬화해 백오프 중 중복 요청 방지
- 이미 실행 중인 감시 서비스는 상품 ON/OFF·앱 재진입 때 내부적으로 중복 초기화하지 않음
- 앱 업데이트/프로세스 재생성 후에는 stale 실행 플래그와 무관하게 감시 서비스 복구
- Android 재부팅 후 켜져 있던 상품 감시 자동 재개
- 최근 7일 진단 이벤트 및 누적 성공/실패/429/타임아웃 통계
- 재고 전환 추적을 위해 `RESTOCK`, `LOW_STOCK`, `SOLD_OUT` 이벤트에 수량/조회 소스를 함께 기록
- 등록 상품/선택 옵션/알림 상태/조회 주기 JSON 백업 및 복원
- WebView 원격 디버깅 비활성화, cleartext 및 파일 접근 차단

## 지원 사이트

### Naver SmartStore

SmartStore 상품 감시는 네이버 로그인이 필요합니다.

- 앱 내부 WebView 쿠키/세션 사용
- 상품 페이지에서 옵션 및 재고 정보 탐색
- 페이지가 자체적으로 받은 SmartStore 상품 응답을 document-start 단계에서 캡처해 재사용하고, 동일 API를 불필요하게 한 번 더 호출하는 빈도를 줄임
- 동일 SmartStore 상품 하나만 감시하는 경우에도 첫 조회 이후 매 주기 페이지를 새로 불러 최신 PAGE_CAPTURE를 사용해 이전 재고 스냅샷을 반복 재사용하지 않음
- 옵션이 없는 상품도 페이지가 이미 받은 정확한 상품 API 응답이면 그대로 재사용해, 후속 동일 API 호출에서 발생하는 204를 피함
- 상품 페이지에 총재고 요약만 있고 실제 옵션 데이터가 없으면 임의의 `기본 상품`으로 확정하지 않고 실제 옵션 데이터/API 조회를 계속 검증
- 저장된 상품 API 정보 우선 재사용 후 실제 API 오류 시 상품 페이지에서 자동 재탐색
- 429 응답은 재탐색 폭주 없이 요청 제한으로 처리
- 204 응답은 기본적으로 상품 단위 실패로 처리하되, 여러 상품에서 연속 발생하는 204 storm은 일시적 서비스/요청 이상으로 보고 5분 보호 대기 후 재개
- 요청 제한 대기 중에는 실제 요청을 보내지 않으며, 대기 상태 자체가 쿨다운 시간을 다시 늘리지 않음
- 만료된 로그인 응답 또는 세션 쿠키 소실을 감지하면 SmartStore 조회를 멈추고 로그인 필요 상태를 유지
- 로그인 성공 후 옵션 조회용 WebView 캐시/히스토리를 비우고 타이머를 재개한 뒤 상품 페이지를 다시 불러옴
- 로그아웃 완료 시 초기 Gate 화면으로 복귀
- 저장된 channelUid가 비어 있어도 기존 상품의 저장된 API URL에서 channelUid를 복구해 페이지 탐색 fallback으로 사용
- 로그인 세션이 만료되어도 SmartStore 상품의 알림 ON 상태는 보존하고 조회만 일시 중지
- 앱 재진입 또는 앱이 열려 있는 상태에서 세션 만료가 확인되면 Gate 로그인 화면으로 전환
- `로그인 없이 시작`을 명시적으로 선택한 경우에만 네이버 세션 없이 메인 화면 사용 가능
- 로그인 필요 상태 알림 표시, 재로그인 성공 시 SmartStore 감시 자동 재개
- 같은 시점에 켜져 있는 SWAGKEY 감시는 계속 유지

### SWAGKEY

SWAGKEY 상품은 네이버 로그인 없이 사용할 수 있습니다.

SWAGKEY는 현재 잔여 수량을 제공하지 않아 재고 부족 알림은 지원하지 않습니다.

- 로그인 화면에서 `로그인 없이 시작`으로 메인 화면 진입 가능
- SWAGKEY 상품만 등록하고 감시 가능
- 앱 재진입 및 기기 재부팅 후에도 켜진 상품이 있으면 감시 재개

## 재입고 판정

처음 조회한 상태는 기준값으로 저장하며 즉시 재입고 알림을 보내지 않습니다.

이후 선택한 옵션이 `품절 → 재고 있음`으로 바뀐 경우에만 재입고 알림을 보냅니다. 정상 응답에서 선택 옵션 일부가 누락되면 품절로 간주하지 않고 해당 조회를 실패 처리하여 마지막 정상 상태를 유지합니다.

SmartStore의 수량을 확인할 수 있는 선택 옵션은 첫 조회에서 이미 기준 이하이면 한 번 알립니다. 이후 기준보다 많다가 기준 이하(1개 이상)로 내려갈 때 다시 알리며, 낮은 수량으로 유지되면 반복하지 않습니다. 품절에서 재입고된 수량 자체가 기준 이하라면 재입고 알림과 함께 저재고 알림도 즉시 보냅니다. 설정의 기준 수량과 조회 주기는 JSON 백업에 포함됩니다. 예전 백업 파일에는 기준 수량이 없으므로 가져올 때 기본값 5개가 적용됩니다.

## 백그라운드 동작

감시는 Foreground Service와 partial WakeLock을 사용합니다. Android 또는 제조사 절전 정책으로 서비스가 중단되는 경우 앱의 **설정 > 백그라운드 실행**에서 배터리 설정을 열고 제한 없는 실행을 허용하는 것을 권장합니다.

재부팅 시 등록된 알림 ON 상품이 있고 Android 알림 권한이 허용되어 있으면 `BootReceiver`가 감시 서비스를 다시 시작합니다.

## 진단

앱의 **설정 > 진단 로그**에서 다음 정보를 확인할 수 있습니다.

- 정상 조회 횟수
- 실패 횟수
- 429 요청 제한 횟수
- 타임아웃 횟수
- 차단된 외부 이동
- 재입고 이벤트
- 마지막 정상 조회 시각
- 최근 7일 이벤트

로그인 쿠키와 상품 응답 본문은 진단 로그에 저장하지 않습니다.

## 데이터 백업

**설정 > 데이터 백업**에서 JSON 파일을 내보내거나 가져올 수 있습니다.

백업 대상:

- 등록 상품
- 선택 옵션
- 상품별 알림 ON/OFF
- 조회 주기

네이버 로그인 쿠키와 세션 정보는 백업하지 않습니다.

## 빌드

Android Studio에서 `android/restock-worker` 디렉터리를 프로젝트로 열어 빌드할 수 있습니다.

- JDK 17
- Android Gradle Plugin 9.4.0
- Gradle 9.6.0
- compileSdk 37
- minSdk 26
- targetSdk 35

GitHub Actions의 **Android Restock Worker APK** workflow는 다음을 자동 검증합니다.

```text
:app:testDebugUnitTest
:app:lintDebug
:app:assembleDebug
```

검증이 모두 성공하면 debug APK, unit test report, lint report artifact가 생성됩니다.

## Release signing

장기 업데이트 설치를 위해 release APK는 고정 keystore로 서명합니다. keystore 파일은 저장소에 커밋하지 않습니다.

수동 실행용 **Android Restock Release APK** workflow는 다음 GitHub Actions Secrets를 사용합니다.

- `RESTOCK_RELEASE_KEYSTORE_BASE64`
- `RESTOCK_RELEASE_STORE_PASSWORD`
- `RESTOCK_RELEASE_KEY_ALIAS`

현재 release keystore는 PKCS12 형식이므로 개인키 비밀번호는 store password와 동일하게 사용합니다. 별도의 `RESTOCK_RELEASE_KEY_PASSWORD` Secret은 필요하지 않습니다. 기존에 등록되어 있다면 삭제해도 됩니다.

모든 secret이 등록된 뒤 workflow를 수동 실행하면 unit test와 lint를 다시 수행한 후 서명된 `app-release.apk`를 artifact로 생성합니다.

기존 debug APK에서 고정 release key로 처음 전환할 때는 서명이 달라 일반 업데이트 설치가 되지 않습니다. 최초 1회는 **JSON 백업 → 기존 debug APK 삭제 → release APK 설치 → JSON 복원 → 네이버 재로그인** 순서로 전환합니다. 이후 release APK는 같은 keystore를 계속 사용하므로 일반 업데이트 설치가 가능합니다.

## 버전

현재 앱 버전: **0.14.42**

204 복구 횟수와 API 호출 정책은 0.14.35 그대로 유지합니다. 페이지 자체 상품 요청의 HTTP 상태/JSON 해석 여부와 앱 API fallback의 204를 구분해 진단합니다. 쿠키·헤더·오류 응답 본문은 기록하지 않습니다. 실패 상태에는 이전 재고 보존과 마지막 정상 확인 시각을 표시합니다(업데이트 이전 값은 시각 미기록). 재입고/품절 이벤트에는 상품 판매 상태를 함께 기록합니다. 204 원인 해결은 실기기 진단 후 판단합니다.

상품 상태 OUTOFSTOCK은 옵션 수량이 남아 있어도 구매 불가로 판정합니다. 원본 옵션 수량은 보존하며 재입고·저재고 알림을 보내지 않습니다. SALE로 돌아오고 선택 옵션에 재고가 있을 때는 재입고 전환을 정상 처리합니다. 204의 서버 측 원인은 미확정입니다.

OUTOFSTOCK 회귀 검증: 저장소 루트에서 `node --test tests/restock-inventory-status.test.mjs` 실행. 캡처·fallback·직접 API 경로와 무옵션 상품, SALE 전환, 옵션 0개/사용불가를 검사하며 Android 빌드 workflow에서도 실행합니다.


### 0.14.39: 페이지 로딩 진단과 진행 중 요청 중복 방지

- 페이지 전용 확인 후에도 감시 상품 API 요청이 진행 중이면 추가 API를 호출하지 않고 `PAGE_REQUEST_PENDING`으로 이번 회차를 마칩니다. 이전 재고를 보존하고 다음 정기 조회에서 다시 확인합니다. 복구 회차의 기존 페이지 전용 확인 횟수·조회 간격·204 보호 대기는 변경하지 않습니다.
- `PAGE_HTTP_ERROR`와 `PAGE_LOAD_ERROR`는 현재 상품 문서 및 관련 스크립트의 상태 코드/오류 코드만 기록합니다. 본문, 요청 헤더, 쿠키, 인증값, 전체 URL은 기록하지 않습니다.
- 실패 진단에 본문 글자 수, 스크립트 수, 스크립트 로딩/실행 오류 수, 탐색 HTTP 상태(미지원 시 unknown), 제한·보안문자 안내 문구의 존재 여부를 추가합니다. 문구 검출만으로 차단으로 확정하지 않습니다.
- `node --test tests/restock-inventory-status.test.mjs tests/restock-page-capture.test.mjs`로 기존 판매 상태/재고 보존 및 진행 중 요청에서 추가 API 미호출을 검증합니다. 디버그·릴리스 GitHub Actions에서도 두 테스트 파일을 모두 실행합니다.
- 실기기에서 오류 재발 후 새 진단 로그 확인이 필요하며 204의 전체 근본 원인은 아직 미확정입니다. 문제가 있으면 0.14.38 코드로 되돌려 더 높은 versionCode로 재빌드합니다(데이터 구조 변경 없음).

### 0.14.41: SmartStore 문서 429를 별도 요청 제한으로 처리

- WebView 메인 문서의 실제 HTTP 429는 로그만 남기지 않고 기존 전역 429 지수 백오프 및 요청 제한 카운터로 연결합니다. 스크립트 429와 다른 상품의 늦은 콜백은 무시합니다.
- 제한된 문서에서 JS 페이지 탐색·내부 API fallback·204 페이지 재로드가 추가 진행되지 않도록 정리하고, 이전 재고·알림 상태를 유지합니다.
- 대기 중에는 SmartStore 재요청을 방지하며 SWAGKEY 조회는 유지합니다. 사용자 설정 10초 및 상품 간 5초 제한은 변경하지 않습니다.
- 10월 27일 운영 로그의 `PAGE_HTTP_ERROR · document · HTTP 429`와 `NO_CONTENT_RETRY` 연쇄를 겨냥한 수정이며, 실제 운영 복구 여부는 업데이트 후 로그로 재확인합니다.
- 롤백은 v0.14.40 로직을 더 높은 versionCode로 빌드합니다. 로컬 사용자 데이터 구조 변경은 없습니다.

### 0.14.42: 반복 429 백오프 조기 초기화 방지

- 정상 재고 조회가 한 번 성공해도 최근 429 페널티를 즉시 지우지 않습니다. 활성 대기만 해제하고, 10분 내 429가 재발하면 기존 단계의 두 배로 기다립니다(최대 30분).
- 마지막 429가 10분보다 오래 지났으면 새 429는 다시 30초부터 시작합니다. 기존 설정 주기(10·15·30·60초), 최소 상품 간격 5초, 재고 상태 보존·SWAGKEY 처리는 변경하지 않습니다.
- v0.14.41 운영 로그에서 429가 90회 관측된 점을 바탕으로 한 요청 제한 대응 개선입니다. 실제 차단 원인을 우회하지 않으며, 제한 후 빠른 재입고 감지가 늦어질 수 있으므로 운영 로그에서 반드시 재검증합니다.
- 롤백: v0.14.41 로직을 새 versionCode로 재빌드할 수 있습니다. 사용자 데이터 스키마 변경은 없습니다.
